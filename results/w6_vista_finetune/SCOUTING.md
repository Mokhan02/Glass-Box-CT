# W6 scouting: fine-tuning NV-Segment-CT (VISTA-3D, `vista3d132`) with bright-tumour augmentation (CPU only, nothing run on a GPU)
Date 2026-11-08, branch `research/roadmap`. Research use only; no clinical claims. **Nothing here has been run on a GPU, no weights were downloaded, no training data was touched.** Estimates are marked as such; the two memory / FLOP numbers come from a shape-only forward pass of MONAI's `vista3d132` on the `meta` device (no allocation, random weights, parameters counted from the real architecture) and need a measured GPU smoke test before any claim.

## 0. Verdict: **GO, conditional** (details in section 6)
Fine-tuning is the officially supported route, the model very likely fits one A10 at the bundle's patch size, the compute is small (about 13 GPU-hours for the whole programme, estimate), and the data (MSD Task03) is already in the project. Conditions: (1) your sign-off on the W6 PREREG (to be written after this), (2) a 50-iteration GPU smoke that measures peak memory and reproduces the W4 baseline VISTA numbers on 10 series, (3) a forgetting guard that is evaluated, not assumed. Main risks: Task03 is **not new data** for VISTA-3D (it was in the original training), forgetting of the other 130 classes, and single runs without seed variance.

## 1. The official fine-tuning path
**What `vista3d132` is.** NV-Segment-CT (132 classes, "commercial friendly", NVIDIA Open Model License) is hosted in [NVIDIA-Medtech/NV-Segment-CTMR](https://github.com/NVIDIA-Medtech/NV-Segment-CTMR), folder `NV-Segment-CT/`; the weights are on [Hugging Face nvidia/NV-Segment-CT](https://huggingface.co/nvidia/NV-Segment-CT) (our pipeline loads `vista3d_pretrained_model/model.pt` into `monai.networks.nets.vista3d132`, `glassbox/seg/infer.py`). The older [Project-MONAI/VISTA](https://github.com/Project-MONAI/VISTA/tree/main/vista3d) repository says the NV-Segment-CT / CTMR code moved to NVIDIA-Medtech.
**The official recipe (the MONAI bundle in `NV-Segment-CT/`):** [`docs/finetune.md`](https://raw.githubusercontent.com/NVIDIA-Medtech/NV-Segment-CTMR/main/NV-Segment-CT/docs/finetune.md): "Users need to provide a json data split for continuous learning"; edit "`label_mappings`, `data_list_file_path`, and `dataset_dir` in `configs/train_continual.json`"; run `python -m monai.bundle run --config_file="['configs/train.json','configs/train_continual.json']"` (multi-GPU: `torchrun --nnodes=1 --nproc_per_node=8 ... configs/multi_gpu_train.json`). "The hyperparameters in `configs/train_continual.json` will overwrite ones in `configs/train.json`." The MONAI model-zoo bundle documents the same procedure ([MONAI/vista3d docs](https://huggingface.co/MONAI/vista3d/blob/main/docs/README.md); its weights carry a different licence, "NCLS v1"; we use the NV-Segment-CT weights).
**Which parts are trainable.** The config freezes nothing: `train.json` has no freeze / `requires_grad` / exclude setting, the optimizer is built from `"$@network.parameters()"` ([`configs/train.json`](https://raw.githubusercontent.com/NVIDIA-Medtech/NV-Segment-CTMR/main/NV-Segment-CT/configs/train.json)) and `scripts/trainer.py` ("Vista3dTrainer") contains no freezing ([`trainer.py`](https://raw.githubusercontent.com/NVIDIA-Medtech/NV-Segment-CTMR/main/NV-Segment-CT/scripts/trainer.py)): **official fine-tuning updates the whole network.** The paper's own Stage 3 is the exception: "We freeze the image encoder to avoid changes to the interactive branch and train the auto branch decoder and head" ([VISTA3D, arXiv 2406.05285](https://arxiv.org/abs/2406.05285)). The doc also says: "The VISTA3D foundation model is trained with interactive only (`drop_label_prob=1`) and then froze the point branch and trained with fully automatic segmentation (`drop_point_prob=1`)"; for automatic-only fine-tuning set `drop_point_prob=1`, `drop_label_prob=0`.
**Parameter groups (measured on the real architecture, `vista3d132(encoder_embed_dim=48)`; random weights):**
| group | parameters | share |
|---|---|---|
| `image_encoder.encoder` (shared SegResNet-type encoder) | 174.95 M | 80.3% |
| `image_encoder.up_layers` (decoder of the interactive / point branch) | 21.16 M | 9.7% |
| `image_encoder.up_layers_auto` (decoder of the automatic branch) | 21.16 M | 9.7% |
| `class_head` (incl. the learnable 512 x 48 class embeddings) | 0.28 M | 0.1% |
| `point_head` | 0.42 M | 0.2% |
| total | 217.96 M | |
With `drop_point_prob=1` only the encoder, `up_layers_auto` and `class_head` receive gradients (the paper's Stage 3 trains only the last two, 21.4 M = 9.8%).
**How class 26 (hepatic tumour) is trained.** There is no tumour-specific code. Every class is a **binary mask learned through a class prompt** (the "N x C class embedding", [paper](https://arxiv.org/html/2406.05285v3): "avoids the partial label problem in training on diverse partially labeled datasets"; absent classes: "train the model to produce zero output when responding to the prompt"). The trainer samples prompts from `label_set` (`sample_prompt_pairs` in MONAI), and the target of each prompt is `labels == prompt_class[id]`; each prompt adds `loss_function(outputs[[id]].float(), labels == prompt_class[id])`, the sum is divided by the number of valid prompts ([`trainer.py`](https://raw.githubusercontent.com/NVIDIA-Medtech/NV-Segment-CTMR/main/NV-Segment-CT/scripts/trainer.py)). Labels are mapped from the user's indices to global VISTA indices (`label_mappings`, e.g. `[[1, 3]]` for the spleen; "Do not map to global index value >= 255"); hepatic tumour is index **26** in [`label_dict.json`](https://raw.githubusercontent.com/NVIDIA-Medtech/NV-Segment-CTMR/main/NV-Segment-CT/configs/label_dict.json) (liver 1, spleen 3, right kidney 5, left kidney 14; the model card also lists "liver tumor" 130; W2 to W5 used class 26). For MSD Task03 the mapping would be `[[1, 1], [2, 26]]`.
**Loss and optimiser (official `train.json`):** `DiceCELoss` with `sigmoid: true`, `squared_pred: true`, `smooth_dr 1e-05`, `to_onehot_y: false`, no term weights; AdamW, `learning_rate 0.0001`, `weight_decay 1e-05`, `WarmupCosineSchedule` (warm-up 3, multiplier 0.1); `batch_size 1`, `patch_size [128,128,128]`, `num_patches_per_image 1`, `drop_label_prob 0.25`, `drop_point_prob 0.25`, `max_point 5`, `amp true`; spacing 1.5 mm isotropic, intensity window -963.8 to 1053.7 HU scaled to [0,1], augmentations `RandCropByLabelClassesd`, `RandScaleIntensityd` and `RandShiftIntensityd` (prob 0.1 each). `train_continual.json` overrides: `finetune: true` (a `CheckpointLoader` from `models/model.pt`), `learning_rate 5e-05`, `lr_schedule#activate false`, cache rates 1.0, example `label_mappings [[1,3]]` on MSD Task09 spleen; the docs' run example uses `--epochs=320 --learning_rate=0.00005`. Number of epochs and the sampler details of `RandCropByLabelClassesd` (tumour-centred sampling ratio) are **TO VERIFY** in the bundle code at preflight.
**Environment.** The model card names "MONAI Core v.1.3" for the tested stack; a third-party wrapper of the bundle pins `monai==1.4.0` because 1.5.x crashed the fine-tune loss on boolean labels (not an official statement). The training environment must therefore be pinned and tested before use (our local MONAI is 1.6.1; the instance environment is to be checked).

## 2. GPU memory: does fine-tuning fit an A10 (24 GB)?
No official figure exists for fine-tuning memory ("No training hardware requirements are given", MONAI docs; the NV-Segment-CT card lists A100 / H100 / L40 as test hardware only). Evidence: the paper trained on "64 32GB NVIDIA V100" GPUs, 128-voxel cubic patch, 36 class prompts per iteration for the automatic branch, and says "the model can be trained with 16GB memory GPUs or even lower by reducing the prompt number in each iteration". The docs' official out-of-memory levers: reduce `patch_size` (example `[96,96,96]`), lower the cache rates, run post-processing on CPU.
**Estimate (meta-device forward, my measurement, not a GPU measurement):** at 128^3, batch 1, two class prompts (liver 1, tumour 26), the sum of all leaf-module outputs is 3.41 G elements (1.38 G conv, 1.01 G norm, 1.01 G activation) = **6.8 GB if kept in fp16 (AMP), 13.6 GB as an upper bound in fp32**; at 96^3 it is 1.44 G elements (2.9 to 5.8 GB). Weights, gradients and AdamW states for all 218 M parameters in fp32: 0.87 + 0.87 + 1.74 = **3.5 GB** (0.3 GB if only the 21 M auto decoder and head are trained). **Peak estimate for the full fine-tune at 128^3: about 12 to 19 GB, i.e. it should fit the A10 (22 GB usable); it does not need an A100.** The number of prompts barely changes it (forward FLOPs 3.98 TFLOP for 2 and for 8 prompts: the encoder dominates). Not covered: the interactive branch (not run with `drop_point_prob=1`) and allocator fragmentation.
**Options if the smoke test shows it does not fit:** (1) `patch_size [96,96,96]` (official lever; changes the receptive context, so it must be applied identically to both arms); (2) freeze the encoder and train the auto decoder and head only (the paper's Stage 3 recipe; memory about 8 GB; but see section 5: it may also limit the effect); (3) gradient checkpointing (`torch.utils.checkpoint` around encoder stages; a code change, slower by about 30%); (4) fewer prompts per patch (the label set has only two classes, so this is already minimal).
**Compute per iteration (estimate):** forward 3.98 TFLOP at 128^3, forward + backward about 11.9 TFLOP; at an effective 15 to 25 TFLOP/s on an A10 with AMP that is **0.5 to 0.8 s per iteration (pessimistic 8 TFLOP/s: 1.5 s)**. For scale: the W4 baseline run measured 17 to 23 s per CT for two sliding-window passes.

## 3. Training data and the augmentation
**Data.** MSD Task03 (131 labelled CTs, labels 1 liver and 2 cancer, CC-BY-SA 4.0; already in the project, W1 and W5), the nnU-Net fold-0 split used in W3 and W5 (about 105 / 26 cases; read `splits_final.json` at preflight): the same fold, so the fine-tune and the W5 nnU-Net models saw the same training cases. **No WAW-TACE and no HCC-TACE-Seg in training, validation or augmentation statistics.** **Caveat that must be stated: Task03 is not new data for VISTA-3D.** The paper's dataset table lists "MSD Task 3,6,7,8,9,10" among its training sources; the W1 audit found bright tumours rare there (MSD Task03 1.1% bright, pooled training sources 5.2% against 32.6% in HCC-TACE-Seg, verdict BRIGHT RARE IN TRAINING). The fine-tune therefore re-trains on volumes the model has already seen, with a different contrast distribution; the Task03 validation fold is NOT independent of VISTA's original training and is used only as a sanity curve. The evidence of transfer is WAW-TACE and HCC-TACE-Seg (never in training).
**The transform.** The W5 BRIGHT transform (`scripts/w5_nnunet_trainer.py`, `shift_tumour_contrast`): for each tumour component of at least 30 voxels, shift the mean HU of the component to a value drawn uniformly between +10 and +60 HU **above the mean of the local liver** (liver voxels within 12 voxels of the component, tumour voxels excluded), Gaussian feathering sigma 1 voxel, edit applied in HU and clipped to the model's window. It must be **ported to physical units for VISTA** (patches at 1.5 mm; shell about 12 mm = 8 voxels; minimum component volume in mm^3; applied after the random crop by inverting VISTA's intensity scaling to HU, editing, and rescaling) and unit-tested on phantoms before use. The SHAM arm uses the same code with a **darkening** shift (uniform -60 to -10 HU, as in W5): same procedure, tumours kept dark, so it separates "any fine-tuning plus any intensity edit" from "bright fine-tuning". An unedited fine-tune ("FT-only") is optional (about 6 GPU-hours).
**Dose: p = 0.25 (fraction of tumour components edited), justification.** In W5 (nnU-Net trained from scratch on Task03, HCC-TACE-Seg held out) the dose-response was saturating: detection gap D0 +0.645, BRIGHT-25 +0.107, BRIGHT-50 +0.090 (C_high = g25 - g5 = -0.000 [-0.045, +0.050]); Dice gap +0.419, +0.201, +0.185 (C_high +0.012 [-0.020, +0.047]; Amendment 4, `results/w5_training/W5_RESULTS.md`). So p = 0.25 reproduced the full-dose effect there and leaves 75% of tumours unedited, which limits distortion of a pretrained model that is being fine-tuned (less drift of other tumour appearances). **Limits of this argument:** one run per dose and no seed-variance estimate (D0-seed2 was not run); the dose-response was measured on a from-scratch nnU-Net, not a fine-tuned foundation model, where the effective dose may differ (few iterations from a strong initialisation); W4 showed that BRIGHT-50 transfers to real arterial tumours, but not what p = 0.25 does there. Optional secondary: p = 0.5 (about 6 GPU-hours).

## 4. Guard against forgetting (pre-specified measurements before and after)
Baseline = the unmodified model, evaluated with the same code. Held-out data are only data not used in the fine-tune:
| what | data | classes | measure |
|---|---|---|---|
| spleen | MSD Task09 (41 CTs, CC-BY-SA 4.0; in VISTA's original training, which is irrelevant for detecting drift) | 3 | Dice, baseline vs fine-tuned, paired |
| kidneys and kidney tumours | C4KC-KiTS (W2 cohort; manual labels; used in W2 with the kidney tumour class) | 5, 14 and the kidney tumour class of W2 | Dice; the kidney tumour gap is a **side check** that bright augmentation of liver tumours does not change another organ's behaviour |
| liver | MSD Task03 validation fold (not independent of VISTA's training; used for the liver, class 1) | 1 | Dice |
| all classes | the same 20 fixed WAW-TACE CTs (random, seed fixed) | all 127 supported, prompts as in the official inference | **prediction drift: Dice between baseline and fine-tuned predictions per class** (needs no labels) |
| false positives | tumour-free Task03 livers (13 cases per the W1 audit) and WAW-TACE liver voxels farther than 10 mm from any ground-truth tumour | 26 | predicted tumour volume outside lesions, baseline vs fine-tuned (bright augmentation could make hyperdense normal structures look like tumour) |
Proposed pass criteria (to be fixed in the PREREG): organ Dice drop at most 0.02 with the CI above -0.03; per-class drift Dice at least 0.95 for organs; no increase of the false-positive tumour volume beyond 25% of the baseline's. TotalSegmentator-derived organ masks of WAW-TACE are model outputs (and define the contrast reference), so they are used only for the drift check on the liver, not as organ ground truth. A failed guard is a result and is reported; the contingency is a lower learning rate, an encoder-frozen variant, or a small replay set of other classes (an amendment, not a silent change).

## 5. Training schedule, and the analysis plan (draft)
**Arms.** (i) BASELINE: the unmodified model; **no new run is needed for the primary comparison** (W4 already scored it on WAW-TACE, W3 on HCC-TACE-Seg; one 10-series reproduction check in the preflight shows the pipeline is unchanged). (ii) BRIGHT-FT (p 0.25, +10 to +60 HU). (iii) SHAM-FT (p 0.25, -60 to -10 HU). Optional: FT-only, BRIGHT-FT seed 2, BRIGHT-FT with p 0.5, and BRIGHT-FT with the encoder frozen.
**Recipe (proposal):** official continual settings: all parameters trainable, AdamW, lr 5e-5, `drop_point_prob 1` (automatic branch only), `drop_label_prob 0`, `patch_size 128^3`, batch 1, AMP, seed fixed per arm, **8,000 iterations** (about 76 epochs of 105 cases; the choice is a budget compromise, not tuned on any outcome), validation on 10 fixed Task03 validation cases every 1,000 iterations, last checkpoint used (no checkpoint selection on any evaluation cohort).
**Evaluation on WAW-TACE (never in training):** exactly the W4 pipeline (class 26 automatic and class 1 for the alignment gate, 396 series, detection = coverage >= 0.10, same scoring, same exclusion and gate sensitivities). (a) gap dark minus bright per arm; (c)-type contrast on the arterial series: **BRIGHT-FT minus BASELINE and minus SHAM-FT** (paired patient bootstrap, CLOSES rule of W5: CI upper < 0 and point <= -0.10); forgetting guard (section 4); secondary replication on HCC-TACE-Seg (the W3 cohort, 75 cases, where the failure was first measured). The within-tumour test is the W4b design (its draft is a separate document), applied to the fine-tuned arms only. **Predictions to state before any run:** SHAM-FT keeps the gap (about the baseline's +0.58 detection gap); BRIGHT-FT narrows it substantially (the direction of W5 BRIGHT-50 on nnU-Net); the size cannot be predicted (W5 was from scratch). Single runs: no seed variance, same limit as W5.
**Why the encoder matters (risk).** The W2-M mechanism work read and edited VISTA's mid-encoder representation of tumour contrast; if the brightness failure lives in the encoder, an encoder-frozen fine-tune might change little (a hypothesis, not a result). That is why the full fine-tune is the primary arm and the frozen-encoder variant an optional contrast.
